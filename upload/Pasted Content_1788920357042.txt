# 8. DOUBLE-ENTRY SAFEGUARD

The finance architecture should be designed with accounting-grade principles.

Where appropriate, use a journal-entry / ledger-entry model so that a financial event can have balanced debit and credit entries.

At minimum, the architecture should support:

```text
Journal / Transaction
    ├── Debit Entry
    └── Credit Entry
```

and for more complex transactions:

```text
Journal
    ├── Entry 1
    ├── Entry 2
    ├── Entry 3
    └── ...
```

The fundamental accounting invariant is:

```text
TOTAL DEBITS = TOTAL CREDITS
```

before a transaction can be posted.

Do not implement fake double-entry where the system simply stores two unrelated amounts.

The database/service layer must validate balancing before posting.

# 13. DATABASE ATOMICITY

Financial postings must be atomic.

Use database transactions.

If any part of a financial posting fails:

```text
NO financial entry should be committed.
```

Never allow:

```text
debit saved
credit failed
```

or:

```text
expense saved
ledger failed
```

or:

```text
income saved
account balance not updated
```

The entire operation must succeed or fail as one unit.

# 14. POSTED TRANSACTIONS MUST NOT BE DESTRUCTIVELY DELETED

This is a critical accounting safeguard.

Once a financial transaction has been posted:

DO NOT allow ordinary users to permanently delete it.

Instead support appropriate states such as:

```text
DRAFT
POSTED
VOIDED
REVERSED
```

If a posted transaction is wrong:

* do not silently edit its financial meaning
* do not delete it
* create a reversal/void mechanism
* preserve the original record
* record who performed the reversal
* record when it occurred
* record the reason

This preserves the audit trail.
