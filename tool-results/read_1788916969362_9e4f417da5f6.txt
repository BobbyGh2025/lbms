   863→CRITICAL ISSUES
   864→==========================================================================
   865→1. PRIVILEGE ESCALATION VIA "md" ROLE ASSIGNMENT
   866→   - File: src/app/api/users/route.ts (POST handler, lines 167-176)
   867→     The roleIds check only verifies that the supplied role IDs exist and are
   868→     not soft-deleted. It does NOT filter out the "md" role. A non-MD user
   869→     with the `users:create` permission can therefore create a new user and
   870→     hand them the MD role, immediately escalating past every permission gate.
   871→   - File: src/app/api/users/[id]/roles/route.ts (PUT handler, lines 70-143)
   872→     The replace-roles handler accepts arbitrary roleIds, validates only
   873→     existence, and writes them inside a transaction. A non-MD user with
   874→     `users:edit` permission can PUT their own user ID with
   875→     `roleIds: ["<md-role-id>"]` and grant themselves MD in a single request.
   876→   - Fix recommendation: in both handlers, fetch the candidate roles'
   877→     `name` field and reject the request with 403 if any role has
   878→     `name === "md"` AND `ctx.isMD === false`. Also gate the same way for
   879→     any future system roles.
   880→
   881→2. LAST-MD ROLE STRIP VIA /api/users/[id]/roles
   882→   - File: src/app/api/users/[id]/roles/route.ts (PUT handler, lines 70-143)
   883→     The PATCH handler at /api/users/[id] (lines 202-212) protects the last
   884→     MD from being deactivated/suspended, and the DELETE handler (lines
   885→     268-276) protects the last MD from being deleted. But the
   886→     PUT /api/users/[id]/roles handler has no equivalent guard. An
   887→     administrator (or the MD themselves) can replace a sole-MD user's
   888→     roleIds with a list that omits "md", instantly stripping system-wide
   889→     admin access with no recovery path.
   890→   - Fix recommendation: before commit, compute the post-replacement MD
   891→     count. If the target user is currently MD, the new roleIds omit "md",
   892→     and no other MD remains, reject with 400.
   893→
   894→3. SELF-DEACTIVATION VIA /api/users/[id]
   895→   - File: src/app/api/users/[id]/route.ts (PATCH handler, lines 136-243)
   896→     The DELETE handler explicitly blocks self-deletion (lines 260-265, with
   897→     a redundant duplicate check). The PATCH handler has no such guard for
   898→     status transitions to `inactive` or `suspended`. A user with
   899→     `users:edit` can suspend their own account, immediately invalidating
   900→     their own session and leaving the system potentially short of an
   901→     active administrator (if they are the only admin-tier user).
   902→   - Fix recommendation: add `if (auth.ctx.userId === id && data.status &&
   903→     data.status !== "active") return forbidden("You cannot deactivate
   904→     your own account.");` near the existing status guard.
   905→
   906→4. JWT-EMBEDDED PERMISSIONS DO NOT REFLECT REVOCATION
   907→   - File: src/lib/auth.ts (callbacks.jwt + session, lines 151-174) and
   908→     src/lib/permissions.ts (loadUserAuthData, lines 66-94)
   909→     Roles and the flattened `permissions` array are loaded ONCE at sign-in
   910→     and embedded in the JWT (8-hour maxAge). When a user's roles are
   911→     changed via /api/users/[id]/roles or /api/roles/[id]/permissions, or
   912→     their account is suspended via /api/users/[id] PATCH, the change is
   913→     NOT reflected until the user re-logs in (or the JWT expires). For up
   914→     to 8 hours a revoked/suspended user retains all prior permissions.
   915→     This is documented as an intentional performance tradeoff, but for a
   916→     system where the primary risk is privilege revocation, a refresh-on-
   917→     mutation hook (or shorter JWT maxAge + DB-backed session strategy)
   918→     should be considered before Phase 2.
