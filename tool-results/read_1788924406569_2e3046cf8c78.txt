   263→## 5. Bugs discovered / fixed
   264→
   265→### 5.1 `src/lib/auth.ts` type coercion
   266→
   267→The NextAuth `authorize` callback returns a user object that needs to be
   268→augmented with `roles`, `permissions`, and `isMD` before being stored on
   269→the JWT. The JWT callback uses `(user as any).roles` etc. because
   270→NextAuth's default `User` type does not include these fields. The type
   271→augmentation in `src/types/next-auth.d.ts` extends the *session* and *JWT*
   272→types, but NextAuth's internal `authorize` return type is not directly
   273→augmentable without a more involved module override.
   274→
   275→**Resolution**: kept the `(user as any)` casts in `auth.ts` callbacks.
   276→They are isolated to three lines in the `jwt` callback, are well
   277→commented, and do not affect runtime behaviour. The remaining TS error
   278→in `auth.ts` (about the augmented session shape) is a known pre-existing
   279→issue tracked for cleanup in Phase 2 when a custom `AuthorizedUser`
   280→interface is introduced.
   281→
   282→### 5.2 Transient module-resolution errors during parallel subagent file writes
   283→
   284→Phase 1 was built by five subagents working in parallel on the Users (2-a),
   285→Roles (2-b), Departments & Positions (2-c), Company Settings (2-d), and
   286→Audit Trail (2-e) modules. Each subagent created files independently; the
   287→shared `view-router.tsx` was authored in Task 1 ahead of the subagents and
   288→already imported all five view components.
   289→
   290→During the brief window where some subagents had finished and others had
   291→not, `bunx tsc --noEmit` reported transient errors for the not-yet-created
   292→view files (e.g. `Cannot find module '@/components/views/users/users-view'`
   293→while Task 2-a was in flight). These errors were purely a side effect of
   294→parallel authoring order, not a defect in any single subagent's work.
   295→
   296→**Resolution**: once all five subagents landed their `View` exports, the
   297→errors resolved themselves. No code change was required — the
   298→`view-router.tsx` import order was already correct. Documented here for
   299→future multi-subagent phases so the orchestrator knows to expect these
   300→transient errors and to re-run `tsc` only after all subagents finish.
   301→
   302→### 5.3 No functional defects
   303→
   304→No functional defects were discovered during Phase 1 verification. Every
   305→acceptance matrix row in `TESTING.md` §3 passed on first manual run.

   378→## A1. Audit findings addressed
   379→
   380→The audit identified three CRITICAL privilege-escalation paths, two
   381→MINOR security gaps, four UI/accessibility nits, and one piece of dead
   382→code. All were addressed:
   383→
   384→### A1.1 Critical security fixes
   385→
   386→1. **Privilege escalation via MD-role assignment** — `POST /api/users`
   387→   and `PUT /api/users/[id]/roles` previously let any user with
   388→   `users:create` / `users:edit` assign the `md` role, including to
   389→   themselves — full privilege escalation in a single request.
   390→   - Files: `src/app/api/users/route.ts`, `src/app/api/users/[id]/roles/route.ts`.
   391→   - Fix: handlers now fetch the candidate roles' `name` field and
   392→     reject the request with HTTP 403 if any candidate is `md` and
   393→     `ctx.isMD === false`.
   394→2. **Last-MD role strip via `PUT /api/users/[id]/roles`** — the PATCH
   395→   handler at `/api/users/[id]` and the DELETE handler already
   396→   protected the last MD; the PUT roles handler did not.
   397→   - File: `src/app/api/users/[id]/roles/route.ts`.
   398→   - Fix: before commit, compute the post-replacement MD count. If the
   399→     target user is currently MD, the new roleIds omit `md`, and no
   400→     other MD remains, reject with 400. Also blocks non-MD users
   401→     from removing the MD role at all.
   402→3. **Self-deactivation via `PATCH /api/users/[id]`** — the DELETE
   403→   handler blocked self-deletion; the PATCH handler did not block
   404→   self-deactivation/suspension.
   405→   - File: `src/app/api/users/[id]/route.ts`.
   406→   - Fix: added a self-deactivation guard that returns 403 when
   407→     `auth.ctx.userId === id && data.status && data.status !== "active"`.
   408→
   409→### A1.2 Minor security fixes
   410→
   411→4. **Dashboard permission enforcement** — `GET /api/dashboard`
   412→   previously only checked session existence; any authenticated user
   413→   could read KPIs.
   414→   - File: `src/app/api/dashboard/route.ts`.
   415→   - Fix: now requires the `dashboard:view` permission. Every seeded
   416→     role already carries `dashboard:view`, so legitimate access is
   417→     unchanged; the route is now correctly gated for the contract.
   418→5. **Audit route error handling** — `GET /api/audit` had no try/catch
   419→   around date parsing or Prisma queries; invalid `from`/`to` dates
   420→   produced unhandled 500s with stack traces in development.
   421→   - File: `src/app/api/audit/route.ts`.
   422→   - Fix: wraps date parsing, Prisma `count`, and `findMany` in a
   423→     single try/catch. Invalid dates now return HTTP 400 with a
   424→     friendly message; unexpected Prisma errors return a generic
   425→     HTTP 500 envelope with no stack trace.
   426→
   427→### A1.3 UI / accessibility fixes
   428→
   429→6. **ThemeToggle hydration mismatch** — `next-themes` resolves the
   430→   theme on the client only, so the toggle rendered `Moon` server-side
   431→   and `Sun` client-side on every page load when a non-default theme
   432→   was stored. The error was harmless but polluted the dev console.
   433→   - File: `src/components/layout/theme-toggle.tsx`.
   434→   - Fix: added a `mounted` guard so the icon is not rendered until
   435→     the theme has resolved client-side.
   436→7. **Settings save-bar a11y** — the `SaveBar` was always mounted and
   437→     visually hidden via CSS `translate-y-full` when the form was
   438→     clean. The hidden buttons were still keyboard-focusable, trapping
   439→     keyboard users.
   440→   - File: `src/components/views/settings/settings-view.tsx`.
   441→   - Fix: `SaveBar` now renders conditionally (`{dirty && <SaveBar/>}`)
   442→     so hidden buttons are not in the tab order.
   443→8. **Departments form `required` announcement** — the Department Name
   444→   and Position Title inputs had a visual `*` asterisk in the label

   547→## A3. Deferred items (Phase 10)
   548→
   549→The following items were considered during the audit but are
   550→acceptable for Phase 1. They are tracked in `SECURITY.md` §15
   551→"Deferred hardening (Phase 10)" and will be revisited in Phase 10:
   552→
   553→- **JWT revocation latency**: permissions and `isMD` are loaded into
   554→  the JWT at sign-in and live for 8 hours. A suspended or revoked
   555→  user retains access until token expiry or re-login. Phase 10 may
   556→  add shorter `maxAge`, a DB-backed session table, or a per-user
   557→  `tokenVersion` column checked on every request.
   558→- **bcrypt cost 10**: acceptable for Phase 1. Production deployments
   559→  could bump to cost 12 (one-line change in `src/lib/auth.ts`); the
   560→  trade-off is ~2× per-login CPU. Old cost-10 hashes continue to
   561→  verify correctly with `bcrypt.compare`; they are re-hashed at the
   562→  new cost on next successful login.
   563→- **Roles hard-delete** (deliberate, not a deferral): `DELETE
   564→  /api/roles/[id]` hard-deletes (with guards: blocks system roles +
   565→  blocks roles with assigned users). Intentional because
   566→  `UserRole`/`RolePermission` cascade-clean. Documented as a
   567→  deliberate design choice in `DATABASE.md` §2.8 and `SECURITY.md`
   568→  §15.
   569→- **Departments/positions manual validation**: uses manual validation
   570→  instead of Zod. Works correctly; lower consistency priority. May
   571→  migrate to Zod in a later cleanup pass.
   572→- **Small-list endpoints without pagination envelope**:
   573→  `/api/roles`, `/api/departments`, `/api/positions`,
   574→  `/api/notifications` return simple arrays/objects without the full
   575→  `{items,total,page,pageSize}` envelope. Acceptable because these
   576→  lists are small and bounded (7 roles, 7 departments, 18 positions,
   577→  30 notifications).
