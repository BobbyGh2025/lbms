   265→   265→
   266→   266→The finance architecture should be designed with accounting-grade principles.
   267→   267→
   268→   268→Where appropriate, use a journal-entry / ledger-entry model so that a financial event can have balanced debit and credit entries.
   269→   269→
   270→   270→At minimum, the architecture should support:
   271→   271→
   272→   272→```text
   273→   273→Journal / Transaction
   274→   274→    ├── Debit Entry
   275→   275→    └── Credit Entry
   276→   276→```
   277→   277→
   278→   278→and for more complex transactions:
   279→   279→
   280→   280→```text
   281→   281→Journal
   282→   282→    ├── Entry 1
   283→   283→    ├── Entry 2
   284→   284→    ├── Entry 3
   285→   285→    └── ...
   286→   286→```
   287→   287→
   288→   288→The fundamental accounting invariant is:
   289→   289→
   290→   290→```text
   291→   291→TOTAL DEBITS = TOTAL CREDITS
   292→   292→```
   293→   293→
   294→   294→before a transaction can be posted.
   295→   295→
   296→   296→Do not implement fake double-entry where the system simply stores two unrelated amounts.
   297→   297→
   298→   298→The database/service layer must validate balancing before posting.
