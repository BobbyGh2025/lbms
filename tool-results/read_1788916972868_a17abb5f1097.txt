    96→   865→1. PRIVILEGE ESCALATION VIA "md" ROLE ASSIGNMENT
    97→   866→   - File: src/app/api/users/route.ts (POST handler, lines 167-176)
    98→   867→     The roleIds check only verifies that the supplied role IDs exist and are
    99→   868→     not soft-deleted. It does NOT filter out the "md" role. A non-MD user
   100→   869→     with the `users:create` permission can therefore create a new user and
   101→   870→     hand them the MD role, immediately escalating past every permission gate.
   102→   871→   - File: src/app/api/users/[id]/roles/route.ts (PUT handler, lines 70-143)
   103→   872→     The replace-roles handler accepts arbitrary roleIds, validates only
   104→   873→     existence, and writes them inside a transaction. A non-MD user with
   105→   874→     `users:edit` permission can PUT their own user ID with
   106→   875→     `roleIds: ["<md-role-id>"]` and grant themselves MD in a single request.
   107→   876→   - Fix recommendation: in both handlers, fetch the candidate roles'
   108→   877→     `name` field and reject the request with 403 if any role has
   109→   878→     `name === "md"` AND `ctx.isMD === false`. Also gate the same way for
   110→   879→     any future system roles.

   112→   881→2. LAST-MD ROLE STRIP VIA /api/users/[id]/roles
   113→   882→   - File: src/app/api/users/[id]/roles/route.ts (PUT handler, lines 70-143)
   114→   883→     The PATCH handler at /api/users/[id] (lines 202-212) protects the last
   115→   884→     MD from being deactivated/suspended, and the DELETE handler (lines
   116→   885→     268-276) protects the last MD from being deleted. But the
   117→   886→     PUT /api/users/[id]/roles handler has no equivalent guard. An
   118→   887→     administrator (or the MD themselves) can replace a sole-MD user's
   119→   888→     roleIds with a list that omits "md", instantly stripping system-wide
   120→   889→     admin access with no recovery path.
   121→   890→   - Fix recommendation: before commit, compute the post-replacement MD
   122→   891→     count. If the target user is currently MD, the new roleIds omit "md",
   123→   892→     and no other MD remains, reject with 400.
