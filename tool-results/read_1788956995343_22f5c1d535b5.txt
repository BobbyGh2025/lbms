   154→### Phase 1 Audit & Hardening Pass
   155→
   156→A read-only audit of every Phase 1 API route and UI component was performed
   157→against the 12-point security checklist and the 7 specific concerns raised
   158→during Phase 1 sign-off. Three critical privilege-escalation paths were
   159→identified and fixed, the dashboard permission gate was closed, error
   160→handling on the audit route was hardened, and four UI/accessibility nits
   161→were addressed. A scripted RBAC probe (one test user per system role,
   162→logged in via the NextAuth credentials flow, probed against 9 protected
   163→endpoints + 2 privilege-escalation attempts + 3 unauthenticated attempts)
   164→returned **14/14 PASS, 0 FAIL**.
   165→
   166→#### Security fixes (critical)
   167→
   168→- **Privilege-escalation guard on MD-role assignment** — `POST /api/users`
   169→  and `PUT /api/users/[id]/roles` now block non-MD users from assigning
   170→  the `md` role. The handlers fetch the candidate roles' `name` field and
   171→  reject the request with HTTP 403 if any candidate is the `md` role and
   172→  the acting user is not MD. Closes the hole where any user with
   173→  `users:create` / `users:edit` could grant themselves (or anyone else)
   174→  full MD access in a single request.
   175→  (`src/app/api/users/route.ts`, `src/app/api/users/[id]/roles/route.ts`)
   176→- **Last-MD guard on role replacement** — `PUT /api/users/[id]/roles` now
   177→  prevents stripping the MD role from the last MD user. If the target
   178→  user is currently MD, the new `roleIds` omit `md`, and no other MD
   179→  remains, the request is rejected. The same handler also blocks non-MD
   180→  users from removing the MD role at all (mirrors the create-side guard).
   181→  (`src/app/api/users/[id]/roles/route.ts`)
   182→- **Self-deactivation block** — `PATCH /api/users/[id]` now blocks a user
   183→  from deactivating or suspending their own account (status transitions
   184→  to `inactive` or `suspended` where `auth.ctx.userId === id`). Brings
   185→  the PATCH handler to parity with the existing DELETE self-deletion
   186→  guard. (`src/app/api/users/[id]/route.ts`)
   187→
   188→#### Security fixes (minor)
   189→
   190→- **Dashboard permission enforcement** — `/api/dashboard` now requires
   191→  the `dashboard:view` permission. Previously the handler only checked
   192→  session existence, so any authenticated user could read KPIs. Every
   193→  Phase 1 role already has `dashboard:view`, so legitimate access is
   194→  unchanged; the route is now correctly gated for the contract.
   195→  (`src/app/api/dashboard/route.ts`)
   196→- **Audit route error handling** — `GET /api/audit` now wraps date
   197→  parsing and Prisma queries in `try`/`catch`. Invalid `from`/`to` query
   198→  params return HTTP 400 with a friendly message instead of an unhandled
   199→  500. (`src/app/api/audit/route.ts`)
   200→
   201→#### UI / accessibility fixes
   202→
   203→- **ThemeToggle hydration fix** — Added a `mounted` guard so the toggle
   204→  icon is not rendered until `next-themes` has resolved the theme
   205→  client-side. Eliminates the SSR/client hydration mismatch that
   206→  polluted the dev console on every page load when a non-default theme
   207→  was stored in `localStorage`.
   208→  (`src/components/layout/theme-toggle.tsx`)
   209→- **Settings save-bar a11y** — `SaveBar` now renders conditionally
   210→  (`{dirty && <SaveBar/>}`) instead of being always mounted and visually
   211→  hidden via CSS `translate-y-full`. Hidden buttons are no longer
   212→  keyboard-focusable when the form is clean.
   213→  (`src/components/views/settings/settings-view.tsx`)
   214→- **Departments form a11y** — Added `required` and `aria-required="true"`
   215→  to the Department Name and Position Title inputs so screen readers
   216→  announce them as required (the visual `*` asterisk in the label was
   217→  already present).
   218→  (`src/components/views/departments/departments-view.tsx`)
   219→- **Tablet breakpoint fix** — `use-mobile.ts` now treats viewport width
   220→  `<= 768` as mobile (was `< 768`). The exactly-768px case (common
   221→  tablet-portrait width) now activates the mobile sidebar overlay drawer
   222→  instead of the desktop sidebar, fixing ~130px horizontal overflow at
   223→  768x1024. (`src/hooks/use-mobile.ts`)
   224→- **Login dev credentials gated** — Demo credentials on the login screen
   225→  now only render when `NODE_ENV !== 'production'`. A note was added
   226→  that production deployments must replace the default passwords before
   227→  going live. (`src/components/auth/login-screen.tsx`)

   265→#### Deferred items (acceptable for Phase 1; targeted for Phase 10)
   266→
   267→- **JWT revocation latency** — permissions are loaded into the JWT at
   268→  sign-in and live for 8 hours. A suspended or revoked user retains
   269→  access until token expiry or re-login. Acceptable for Phase 1;
   270→  Phase 10 may add shorter `maxAge` or DB-backed session validation.
   271→- **bcrypt cost 10** — acceptable for Phase 1. Production deployments
   272→  could bump to cost 12 (a one-line change in `src/lib/auth.ts`); the
   273→  trade-off is ~2× per-login CPU.
   274→- **Roles hard-delete** — `DELETE /api/roles/[id]` hard-deletes (with
   275→  guards: blocks system roles + blocks roles with assigned users).
   276→  Intentional because `UserRole`/`RolePermission` cascade-clean.
   277→  Documented as a deliberate design choice in `DATABASE.md` §2.8.
   278→- **Departments/positions manual validation** — uses manual validation
   279→  instead of Zod. Works correctly; lower consistency priority. May
   280→  migrate to Zod in a later cleanup pass.
   281→- **Small-list endpoints without pagination envelope** — `/api/roles`,
   282→  `/api/departments`, `/api/positions`, `/api/notifications` return
   283→  simple arrays/objects without the full `{items,total,page,pageSize}`
   284→  envelope. Acceptable because these lists are small and bounded
   285→  (7 roles, 7 departments, 18 positions, 30 notifications).

   287→### Documented assumptions
   288→- Per spec §50: the original LBMS specification called for a
   289→  PHP / CodeIgniter 3 / MySQL implementation. After architecture review the
   290→  team standardised on a single TypeScript stack (Next.js 16 + Prisma +
   291→  SQLite + NextAuth v4 + Tailwind 4 + shadcn/ui). The schema is
   292→  provider-agnostic; switching to MySQL later requires only a `provider`
   293→  change in `prisma/schema.prisma` and a `prisma migrate` run. Money
   294→  (Decimal) fields are deferred to Phase 2 so they land in a
   295→  MySQL-compatible database from day one of the finance modules. All other
   296→  functional requirements of the spec are honoured by this
   297→  implementation.

   320→## [Unreleased] — Phase 2 Finance Foundation

   322→### Phase 2 — Finance Foundation
   323→
   324→Phase 2 ships the LBMS finance core as a journal/ledger double-entry
   325→system: every financial event is a `Journal` with two or more
   326→`JournalEntry` rows whose debits and credits must balance. Balances are
   327→**derived** from posted journal entries (no mutable `currentBalance`
   328→field); the dashboard and finance reports consume a single reporting
   329→service that is the source of truth for every total. All postings run
   330→through one authoritative posting engine inside `db.$transaction`, all
   331→money uses Prisma `Decimal` (decimal.js) and serializes to STRING on
   332→the wire, and reversals preserve the original journal (mirrored entries
   333→net to zero). 15 accounting scenario tests pass and the dashboard's
   334→financial KPIs are now real.
   335→
   336→#### Added — Database (6 new models)
   337→
   338→- `FinancialAccount` — where money lives (cash/bank/momo). `code` +
   339→  `name` unique; `accountType` (asset|liability); `currency`;
   340→  `openingBalance` (Decimal — the seed value posted as an
   341→  OPENING_BALANCE journal, never updated by transactions); `status`;
   342→  `bankName` + `accountNumber`; soft-delete; `createdById` FK to `User`.
   343→- `LedgerAccount` — chart of accounts. `code` + `name` unique;
   344→  `accountClass` (asset|liability|equity|income|expense); `accountType`;
   345→  `currency`; `status`; `isSystem` flag (seeded categories can be
   346→  deactivated but not deleted); soft-delete; `createdById` FK to `User`.
   347→- `Journal` — one financial event. `reference` (unique, generated
   348→  concurrency-safe inside `db.$transaction` via `FinanceRefCounter`);
   349→  `transactionType` (income|expense|transfer|opening_balance|adjustment);
   350→  `status` (draft|posted|voided|reversed); `transactionDate` (the
   351→  accounting date, distinct from `createdAt`); description/notes;
   352→  `financialAccountId` + `ledgerAccountId` (primary references);
   353→  `departmentId` (existing); `partyType` + `partyRef` (nullable stubs
   354→  for Phase 5 Customer/Supplier); `projectRef` (nullable stub for Phase
   355→  6 Project); `paymentMethod`; `externalRef`; `reversesId` +
   356→  `reversedBy` (self-relation for reversals); `reversalReason`;
   357→  `amount` (Decimal); `currency`; `createdById` (required FK);
   358→  `postedAt`; `voidedAt` + `voidedById`; timestamps.
   359→- `JournalEntry` — debit/credit lines (at least 2 per journal). Exactly
   360→  one of `debit` / `credit` is non-zero per row. `financialAccountId`
   361→  is OPTIONAL — only cash-side entries reference a financial account;
   362→  income/expense category lines reference only a `ledgerAccountId`.
   363→  This mirrors real accounting where income/expense categories are not
   364→  "accounts you hold money in".
   365→- `FinanceRefCounter` — concurrency-safe reference counter (one row per
   366→  `prefix + year`). Incremented inside the posting transaction to
   367→  guarantee unique references even under concurrent inserts.
   368→  `@@unique([prefix, year])`.
   369→- `FinanceIdempotencyLog` — optional idempotency-key log for duplicate-
   370→  submit protection. Phase 2 ships the model; consumption is wired in
   371→  later phases.
   372→
   373→#### Added — Finance service layer (`src/lib/finance/`)
   374→
   375→- `money.ts` — centralized Decimal handling. Exports `toMoney`,
   376→  `toPositiveMoney`, `roundMoney`, `addMoney`, `subMoney`, `moneyEq`,
   377→  `isZero`, `serializeMoney` (returns STRING), `formatMoney` (returns
   378→  "GHS 5,000.00"), `formatAmount` (no currency code), `ZERO` sentinel,
   379→  `Money` type alias, and `MoneyError` class. Money flows as
   380→  `Prisma.Decimal` on the server and is serialized to STRING on the
   381→  wire to avoid JavaScript floating-point corruption.
   382→- `constants.ts` — canonical domain constants: `TRANSACTION_TYPES`,
   383→  `JOURNAL_STATUSES`, `ACCOUNT_CLASSES`, `PAYMENT_METHODS`,
   384→  `PARTY_TYPES`, `REF_PREFIXES` (INC/EXP/TRF/OPB/ADJ). Validation
   385→  helpers `isTransactionType`, `isPaymentMethod`, `isAccountClass`.
   386→- `posting-engine.ts` — THE single authoritative poster. `postJournal`
   387→  validates → normalizes → verifies Σ(debit) = Σ(credit) → posts
   388→  atomically in `db.$transaction` → writes audit log. Convenience
   389→  builders: `postIncome` (debit financial account, credit income
   390→  ledger — income category has NO financial account), `postExpense`
   391→  (debit expense ledger, credit financial account), `postTransfer`
   392→  (debit to-account, credit from-account, neither income nor expense
   393→  affected). `reverseJournal` mirrors the entries and marks the
   394→  original as `reversed` (original is preserved, never deleted).
   395→  Errors: `FinanceValidationError` (HTTP 400) and
   396→  `FinanceBalanceError` (subclass).
   397→- `reporting.ts` — THE single source of truth for balances and
   398→  summaries. `getAccountBalance`, `listAccountBalances`,
   399→  `getTotalCashPosition`, `getFinanceSummary`, `getCashFlowSeries`,
   400→  `listTransactions` (paginated, filtered), `getTransactionDetail`
   401→  (with journal entries), `runReconciliation` (verifies all posted
   402→  journals balance). Income/expense totals derive from ledger entries
   403→  (credit−debit for income, debit−credit for expense) so reversals
   404→  net out correctly.

   488→#### Key accounting decisions documented
   489→
   490→1. **Balances are DERIVED** from posted `JournalEntry` rows — no
   491→   mutable `currentBalance` field. Opening balance is posted as an
   492→   OPENING_BALANCE journal so it is already in the entry totals (NOT
   493→   double-counted).
   494→2. **Double-entry**: every journal has ≥2 entries; Σ(debit) =
   495→   Σ(credit) enforced before posting.
   496→3. **Atomicity**: all postings via `db.$transaction`. If any part
   497→   fails, nothing commits.
   498→4. **Reversals, not deletes**: posted journals cannot be deleted.
   499→   Reversal creates a mirrored journal; the original is marked
   500→   "reversed" and preserved. Both stay in balances (they net to zero).
   501→5. **Balance inclusion**: `posted` + `reversed` journals affect
   502→   balances (the reversed original + its reversal net to zero).
   503→   `draft` and `voided` are excluded.
   504→6. **Income/expense totals** derive from ledger entries (credit−debit
   505→   for income, debit−credit for expense), NOT from journal header
   506→   amounts — so reversals net out correctly.
   507→7. **Money precision**: Prisma `Decimal` (decimal.js). On SQLite stored
   508→   as TEXT (no precision enforcement at DB level); on PostgreSQL/MySQL
   509→   migrates to `DECIMAL(18,2)` with zero schema change. App-layer
   510→   validation enforces precision in dev.
   511→8. **Currency**: GHS default (configurable via `CompanySetting`).
   512→   All entries in a journal must share one currency (cross-currency
   513→   not supported in Phase 2).
   514→9. **References**: `INC-2026-000001` format. Concurrency-safe via
   515→   `FinanceRefCounter` incremented inside the posting transaction.
   516→10. **Customer/Supplier/Project**: nullable stub fields
   517→    (`partyType`/`partyRef`/`projectRef`) on `Journal` — connect to
   518→    Phase 5/6 entities without migration.
   519→
   520→#### Database decision (SQLite + Decimal without `@db` annotation)
   521→
   522→- SQLite remains the dev database (environment constraint —
   523→  PostgreSQL/MySQL not available in this sandbox).
   524→- Prisma `Decimal` is used for all money fields. Stored as TEXT in
   525→  SQLite; migrates to `DECIMAL(18,2)` on PostgreSQL/MySQL.
   526→- The `@db.Decimal(18,2)` native annotation is **intentionally
   527→  omitted** so the schema works on both SQLite and PostgreSQL/MySQL
   528→  without modification. App-layer validation enforces precision in
   529→  dev.
   530→- Production MUST use PostgreSQL 16+ or MySQL 8+ for: row-level
   531→  locking on concurrent balance updates, DB-level Decimal precision
   532→  enforcement, and proper transaction isolation.
   533→- The schema is migration-ready: switch `provider = "postgresql"`
   534→  (or `"mysql"`) and run `prisma migrate` — no schema changes needed.

   536→### Known limitations (Phase 2)
   537→
   538→- Cross-currency transactions are not supported (all entries in a
   539→  journal must share one currency).
   540→- No multi-currency conversion.
   541→- No recurring transactions.
   542→- No budget tracking (Phase 3).
   543→- No accounts receivable / payable workflows (Phase 3).
   544→- No customer/supplier linkage on journals (`partyType` + `partyRef`
   545→  stubs await Phase 5 entities).
   546→- No project linkage on journals (`projectRef` stub awaits Phase 6).
   547→- No paginated CSV export API (the reports view builds CSV client-side
   548→  from the summary JSON; a streaming export API is a Phase 10 nice-to-
   549→  have).
   550→- The `FinanceIdempotencyLog` table ships but is not yet consumed by
   551→  the API layer (deferred to a Phase 3 hardening pass).
