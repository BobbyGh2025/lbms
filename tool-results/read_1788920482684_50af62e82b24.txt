   228→
   229→Do NOT create unrelated tables such as:

   232→income
   233→expenses

   243→
   244→The financial system should conceptually follow:
   245→
   246→```text
   247→Financial Accounts
   248→        ↓
   249→Financial Transactions / Journal
   250→        ↓
   251→Ledger / Entries
   252→        ↓
   253→Account Balances
   254→        ↓
   255→Reports
   256→        ↓
   257→Executive Dashboard
   258→```
   259→
   260→The system must have ONE authoritative source for financial movement.

   264→# 8. DOUBLE-ENTRY SAFEGUARD
   265→
   266→The finance architecture should be designed with accounting-grade principles.
   267→
   268→Where appropriate, use a journal-entry / ledger-entry model so that a financial event can have balanced debit and credit entries.
   269→
   270→At minimum, the architecture should support:
   271→
   272→```text
   273→Journal / Transaction
   274→    ├── Debit Entry
   275→    └── Credit Entry
   276→```
   277→
   278→and for more complex transactions:
   279→
   280→```text
   281→Journal
   282→    ├── Entry 1
   283→    ├── Entry 2
   284→    ├── Entry 3
   285→    └── ...
   286→```
   287→
   288→The fundamental accounting invariant is:
   289→
   290→```text
   291→TOTAL DEBITS = TOTAL CREDITS
   292→```
   293→
   294→before a transaction can be posted.
   295→
   296→Do not implement fake double-entry where the system simply stores two unrelated amounts.
   297→
   298→The database/service layer must validate balancing before posting.
