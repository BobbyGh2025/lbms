     1→# Database
     2→
     3→This is the Phase 1 data dictionary for LBMS. The schema is defined in
     4→`prisma/schema.prisma` and uses SQLite as the active datasource (with a
     5→MySQL-compatible schema — see §10 below).
     6→
     7→---
     8→
     9→## 1. Datasource
    10→
    11→```prisma
    12→generator client {
    13→  provider = "prisma-client-js"
    14→}
    15→
    16→datasource db {
    17→  provider = "sqlite"
    18→  url      = env("DATABASE_URL")
    19→}
    20→```
    21→
    22→- `DATABASE_URL` is set in `.env` to `file:./db/custom.db`.
    23→- The Prisma client is generated into `node_modules/.prisma/client` and
    24→  re-exported from `src/lib/db.ts` as a singleton.
    25→- Schema is applied via `bun run db:push` (`prisma db push --accept-data-loss`)
    26→  in development. See `DEPLOYMENT.md` for migration procedures.

    30→## 2. Models (alphabetical)
    31→
    32→### 2.1 `AuditLog`
    33→
    34→Immutable record of important actions. Append-only at the application layer.
    35→
    36→| Field | Type | Constraints |
    37→| --- | --- | --- |
    38→| `id` | String | `@id @default(cuid())` |
    39→| `userId` | String? | nullable; FK to `User.id` (`onDelete: SetNull`) |
    40→| `user` | User? | relation back to User |
    41→| `action` | String | one of `login | logout | login_failed | create | update | delete | approve | reject | view_sensitive | export | system` |
    42→| `module` | String | `auth | users | roles | settings | departments | positions | employees | notifications | system | ...` |
    43→| `recordId` | String? | nullable |
    44→| `recordType` | String? | nullable; e.g. `User`, `Role`, `Department`, `Position`, `CompanySetting`, `RolePermission`, `seed` |
    45→| `description` | String? | human-readable summary |
    46→| `ipAddress` | String? | from `x-forwarded-for` / `x-real-ip` |
    47→| `userAgent` | String? | from `user-agent` header |
    48→| `previousValue` | String? | JSON string of prior state |
    49→| `newValue` | String? | JSON string of new state |
    50→| `createdAt` | DateTime | `@default(now())` |
    51→

    53→

    55→call against `AuditLog` anywhere in the codebase. The only writer is
    56→`recordAudit()` in `src/lib/audit.ts`, which is invoked from `auditFromCtx()`
    57→in route handlers and directly in `src/lib/auth.ts`. There are also no
    58→`POST`/`PATCH`/`DELETE` HTTP endpoints on `/api/audit`.

   202→| `name` | String | `@unique`; regex `^[a-z][a-z0-9_]*$` |

   287→## 3. Entity-relationship description
   288→
   289→```
   290→User ─< UserRole >─ Role ─< RolePermission >─ Permission
   291→  |                                                    |
   292→  |  employeeId (1:1)                                  |
   293→  v                                                    |
   294→Employee >── Department ───< Position                  |
   295→  |            |             |                          |
   296→  |            |  positions |                          |
   297→  |            v            v                          |
   298→  |     Department ─< Position ─< Employee             |
   299→  |                                                    |
   300→  |<──── Notification                                  |
   301→  |                                                    |
   302→  └──── AuditLog (FK userId, onDelete: SetNull) ───────┘
   303→
   304→CompanySetting (singleton, no FKs)
   305→```
   306→
   307→Key cardinalities:
   308→
   309→- `User ↔ Role` is many-to-many through `UserRole`.
   310→- `Role ↔ Permission` is many-to-many through `RolePermission`.
   311→- `User ↔ Employee` is one-to-one (`User.employeeId` is `@unique`).
   312→- `Department → Position → Employee` is a hierarchy; `Department.headEmployeeId`
   313→  is reserved for Phase 4 (no FK relation defined yet).
   314→- `Employee → Department` and `Employee → Position` are nullable
   315→  (`onDelete: SetNull`).
   316→- `AuditLog → User` is nullable (`onDelete: SetNull`) so audit entries
   317→  survive user deletion.
   318→- `Notification → User` is non-nullable with `onDelete: Cascade` so
   319→  notifications are cleaned up when a user is hard-deleted (soft-deleted
   320→  users keep their notifications).

   421→## 5. Soft-delete convention
   422→
   423→Models that support soft-delete carry a nullable `deletedAt: DateTime?`
   424→column:
   425→
   426→- `User.deletedAt`
   427→- `Role.deletedAt` (retained for create-restore logic; roles are hard-deleted)
   428→- `Department.deletedAt`
   429→- `Position.deletedAt`
   430→- `Employee.deletedAt`
   431→
   432→The read paths in every API route filter `deletedAt: null` via the
   433→`notDeleted()` helper in `src/lib/api-helpers.ts`:
   434→
   435→```ts
   436→export function notDeleted() {
   437→  return { deletedAt: null };
   438→}
   439→```
   440→
   441→`CompanySetting`, `Permission`, `RolePermission`, `UserRole`, `AuditLog`
   442→and `Notification` do **not** support soft-delete.

   446→## 6. Singleton `CompanySetting` pattern
   447→
   448→`CompanySetting` is a single-row table. The primary key is
   449→`@default("singleton")` so the row always has `id = "singleton"`. This
   450→gives us:
   451→
   452→- A single source of truth for currency, address, invoice prefix etc.
   453→- No need for a `WHERE` clause on `findUnique` — the singleton id is
   454→  hard-coded in `src/app/api/company-settings/route.ts`.
   455→- Defensive create-on-read: if the row is somehow missing, the GET
   456→  handler creates it with Prisma defaults.
   457→
   458→There is no list endpoint and no `id` parameter on the route. The PUT
   459→upserts onto the singleton key, capturing `previousValue` + `newValue` for
   460→the audit trail.

   464→## 7. Audit log immutability convention
   465→
   466→`AuditLog` is **append-only**. There is no `prisma.auditLog.update()` or
   467→`prisma.auditLog.delete()` call anywhere in the codebase. The HTTP surface
   468→only exposes `GET /api/audit` and `GET /api/audit/stats`. The schema
   469→deliberately has no `updatedAt` or `deletedAt` column on `AuditLog` — it
   470→is a write-once, read-many table.
   471→
   472→`previousValue` and `newValue` are stored as JSON strings (the schema
   473→column type is `String`). `recordAudit()` serialises them with
   474→`JSON.stringify()` before writing.

   478→## 8. SQLite-specific notes
   479→
   480→### No native enums
   481→
   482→SQLite has no native `ENUM` type, so all "enum-like" fields are stored as
   483→`String` and validated at the application layer:
   484→
   485→- Zod schemas in mutation routes enforce the allowed values (e.g.
   486→  `z.enum(["active", "inactive", "suspended"])` in the user PATCH schema).
   487→- A small `STATUS_VALUES = new Set(["active", "inactive"])` constant is
   488→  used in `departments/[id]/route.ts` and `positions/[id]/route.ts`.
   489→- `AuditAction` is a TypeScript union in `src/lib/audit.ts` but is stored
   490→  as a plain `String` column.
   491→
   492→### Decimal money fields deferred to Phase 2
   493→
   494→SQLite's `Decimal` support is approximate (it stores as `REAL`). The
   495→finance modules in Phase 2 require precise money math, so all money fields
   496→are deferred until the datasource can be switched to MySQL (or PostgreSQL).
   497→Phase 1 has no money columns.
   498→
   499→**Production database requirement (added in Phase 1 audit documentation
   500→pass)**: Phase 2 money columns will use Prisma's `Decimal` type with a
   501→native-type extension `@db.Decimal(18,2)`. This extension **requires**
   502→the `mysql` or `postgresql` datasource provider — it silently does not
   503→apply on `sqlite`. The recommendation is therefore to migrate from
   504→SQLite to MySQL/Postgres **before** Phase 2 lands, so that money
   505→precision is enforced at the DB layer from day one.
   506→
   507→See `ARCHITECTURE.md` §16 "Technology decision & production database
   508→strategy" for the full migration plan and the list of SQLite-specific
   509→risks (no row-level locking, no native enums, no `@db.Decimal`/`@db.VarChar`
   510→native type extensions). The recommended production databases are
   511→PostgreSQL 16+ (preferred) or MySQL 8+ (matches the original spec's DB
   512→choice). Both migrate cleanly from the current Phase 1 schema with a
   513→single `provider` change in `prisma/schema.prisma`.
   514→
   515→### Case-insensitive matching
   516→
   517→SQLite's default `contains` filter is case-insensitive for ASCII text.
   518→This is fine for Phase 1's small search surfaces (department / position /
   519→audit search). A MySQL migration may need explicit collation choices for
   520→case-insensitive search.
   521→
   522→### `@unique` and soft-delete interaction
   523→
   524→Soft-deleted rows still occupy `@unique` constraints in SQLite. The create
   525→endpoints handle this explicitly:
   526→
   527→- The roles POST handler checks for a soft-deleted role with the same
   528→  name and "restores" it instead of failing the unique constraint.
   529→- The users POST handler surfaces a friendly message if a soft-deleted
   530→  email or username collides with the requested new user.

   534→## 9. Migration path
   535→
   536→### Phase 1 (current): `prisma db push`
   537→
   538→Development uses `bun run db:push` (`prisma db push --accept-data-loss`).
   539→This is acceptable because Phase 1 is in active development and there is
   540→no production data to preserve. `--accept-data-loss` is used so column
   541→type changes do not block the push.
   542→
   543→### Phase 2+ (production): `prisma migrate`
   544→
   545→Once Phase 2 ships and real data exists, the project will switch to
   546→`prisma migrate`:
   547→
   548→```bash
   549→bun run db:migrate    # creates + applies a migration in dev
   550→# in production:
   551→npx prisma migrate deploy
   552→```
   553→
   554→`prisma/migrations/` will start being populated from Phase 2 onward.
   555→Phase 1's `prisma db push` history is intentionally not checked in.
   556→
   557→### MySQL migration
   558→
   559→To switch from SQLite to MySQL:
   560→
   561→1. Update `prisma/schema.prisma`:
   562→   ```prisma
   563→   datasource db {
   564→     provider = "mysql"
   565→     url      = env("DATABASE_URL")
   566→   }
   567→   ```
   568→2. Promote enum-like `String` columns to native MySQL `enum(...)` types if
   569→   desired (Prisma will then enforce them at the DB level).
   570→3. Run `prisma migrate reset` against the new MySQL instance and re-seed
   571→   with `bun run db:seed`.
   572→
   573→No application code changes are required — the Prisma client API is the
   574→same for both providers.

   602→## 11. Financial architecture readiness (Phase 1 audit documentation)
   603→
   604→The Phase 1 schema is **stable** and will host the Phase 2 finance
   605→modules without modification. This section records the contract between
   606→the Phase 1 schema and the future finance tables.
   607→
   608→### 11.1 Stable Phase 1 tables (no changes in Phase 2+)
   609→
   610→The following Phase 1 tables are referenced by the future finance
   611→system and will **not** be modified:
   612→
   613→- `User` — every financial transaction is created by and audited against
   614→  a `User`. The `createdById` self-relation pattern (already used on
   615→  `User` and `Role`) is reused for finance records.
   616→- `Department` — finance reports group by department; project expenses
   617→  may reference a department.
   618→- `AuditLog` — every financial mutation writes a `previousValue` +
   619→  `newValue` snapshot via `recordAudit()` (the only writer to
   620→  `AuditLog`). Finance transactions use the same audit pipeline.
   621→- `CompanySetting` — currency, invoice prefix, financial year start.
   622→  Phase 2 reads but does not modify this row.
   623→- `Notification` — approval flows, invoice due dates, payment reminders
   624→  all write rows here using the same `Notification` schema (the
   625→  `category` field already reserves values like `invoice`, `payment`,
   626→  `deadline`, `approval`).
   627→
   628→### 11.2 New tables added in Phase 2
   629→
   630→Phase 2 will **add** the following tables (none requires modifying any
   631→existing table):
   632→
   633→- `Account` — cash & bank accounts. Columns: `openingBalance` (Decimal
   634→  `@db.Decimal(18,2)`), `currency` (3-letter ISO code, mirrors
   635→  `CompanySetting.currency`), `type` (`cash | bank | mobile_money`),
   636→  soft-delete columns. All financial transactions reference an
   637→  `Account`.
   638→- `Category` — income categories and expense categories (one table
   639→  with a `type` discriminator, or two tables — TBD in Phase 2 design).
   640→- `Customer` (Phase 5) and `Supplier` (Phase 5) — master data for
   641→  accounts receivable / accounts payable.
   642→- `Project` (Phase 6) — projects that income/expenses can be attributed
   643→  to for profitability analysis.
   644→- `Transaction` — the ledger row. Columns: `type` field
   645→  (`income | expense | transfer | adjustment`), `amount` (Decimal
   646→  `@db.Decimal(18,2)`), `accountId` (FK to `Account`), `categoryId`
   647→  (FK to `Category`), `createdById` (FK to `User`), optional
   648→  `customerId`, `supplierId`, `projectId`, `departmentId`. Timestamps
   649→  via `createdAt`; immutable once written (no `PATCH` on
   650→  `Transaction` — corrections are new rows with `type: "adjustment"`
   651→  referencing the original).
   652→
   653→The `cuid()` ID strategy used throughout Phase 1 (every `@id` is
   654→`@default(cuid())`) is suitable for the ledger — ledger rows are
   655→immutable once written and never need sequential IDs.
   656→
   657→### 11.3 The balance-derivation principle (key invariant)
   658→
   659→**Account balances MUST be derived, never stored as a mutable field
   660→updated by writes.** The displayed balance of an Account at any time T
   661→is:
   662→
   663→```
   664→balance(T) = openingBalance
   665→           + sum(amount for transactions where type = 'income'  and createdAt <= T)
   666→           - sum(amount for transactions where type = 'expense' and createdAt <= T)
   667→```
   668→
   669→This invariant preserves financial integrity and auditability:
   670→
   671→- The balance is always recomputable from immutable history. An
   672→  attacker who modifies a balance column cannot hide the discrepancy —
   673→  the derived total will diverge from the stored total.
   674→- The audit trail's `previousValue`/`newValue` JSON snapshots capture
   675→  every transaction; the running balance is a pure function of the
   676→  audit trail.
   677→- Period-close operations can freeze a balance snapshot (cache the
   678→  derived value at close time) without ever writing the balance back
   679→  to the `Account` row as a "current" field.
   680→
   681→Phase 2 may add a cached `currentBalance` column on `Account` for
   682→dashboard performance, but it MUST be a derived read-model updated by
   683→the same `db.$transaction` that writes the `Transaction` row — never
   684→directly writable by the API.
   685→
   686→### 11.4 SQLite-specific risk summary for the migration
   687→
   688→When the Phase 2 migration to MySQL/Postgres happens, the following
   689→SQLite-specific behaviours must be considered (the same list appears
   690→in `ARCHITECTURE.md` §16.5; it is duplicated here for the
   691→data-dictionary reader):
   692→
   693→- **`Decimal` type**: Prisma maps `Decimal` to `TEXT` in SQLite (no
   694→  precision enforcement) but to `DECIMAL(p,s)` in MySQL/Postgres. In
   695→  dev the app layer must validate precision; in production the DB
   696→  enforces it natively. Any existing dev data with out-of-precision
   697→  Decimals would fail the migration.
   698→- **No native enums**: the schema uses `String` + app-layer validation
   699→  (Zod `z.enum(...)` in mutation routes, `STATUS_VALUES` Set in
   700→  `[id]/route.ts` files). Prisma `enum` types are available on
   701→  MySQL/Postgres; a future migration could promote status/action fields
   702→  to native enums (optional, not blocking).
   703→- **No row-level locking**: concurrent balance updates in SQLite are
   704→  serialised at the DB level (correct but slow). Production must use
   705→  MySQL/Postgres with `$transaction` + appropriate isolation
   706→  (`SERIALIZABLE` or `SELECT ... FOR UPDATE`).
   707→- **No `@db.Decimal`, `@db.VarChar` native type extensions** in SQLite.
   708→  Any such annotations added in Phase 2 will silently not apply on
   709→  SQLite, so dev with SQLite would not catch precision violations. The
   710→  recommendation is to migrate to MySQL/Postgres **before** Phase 2
   711→  lands.
